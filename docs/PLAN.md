## 1. Что требует задание

Обязательно:

1. **Выплата купона** — определить держателей на дату отсечки, посчитать права, выплатить onchain или инициировать расчёт.
2. **Погашение** — в дату погашения определить держателей, посчитать номинал, провести расчёт, **погасить (сжечь) токены**.
3. **Одно дополнительное корпоративное действие** — выбираем **частичное досрочное погашение** (амортизация номинала).

Прототип должен содержать: тестовый токенизированный инструмент с реестром держателей, механизм даты отсечки, логику расчёта прав, рабочие купон и погашение, доп. действие, проверяемую onchain-запись результатов. Банковские рельсы можно симулировать, логика на Solana должна быть рабочей.

Сдаём: прототип, видео, репозиторий, техническое описание (архитектура, логика отсечки, расчёт прав, поток расчётов, компоненты Solana), **явное разделение «реализовано / симулировано»**.

Критерии: техническое исполнение 30%, логика корпоративных действий 25%, продукт и UX 20%, применимость 15%, новизна 10%.

## 2. Продукт простыми словами

Когда компания занимает деньги у многих инвесторов через облигации, кто-то должен помнить, кто сейчас владеет бумагами, посчитать, сколько кому положено, и разнести деньги. Сегодня это делают депозитарий, платёжный агент и бухгалтерия — со сверками и днями задержки.

PRITOK — **реестр и платёжный агент в одной программе**:

- реестр держателей в блокчейне, актуальный в каждую секунду;
- выплаты по графику, который никто не может тихо поменять;
- каждый расчёт и каждая выплата проверяются по ссылке;
- если эмитент не заплатил вовремя, это видно сразу;
- деньги идут либо onchain (стейблкоин), либо через банк — с onchain-учётом поручений и подтверждений.

Мы **не** делаем биржу: выпуск и торги остаются за торговой площадкой. Мы — слой обслуживания выпуска после размещения.

## 5. Архитектура

### 5.0 Ключевое решение: облигации всегда заморожены, двигает их только программа

Первая версия плана строилась на transfer hook. Независимое ревью (2026-09-27) нашло, что реестр при этом можно изменить в обход hook: владелец сам сжигает токены (`BurnChecked` hook не вызывает) или передаёт контроль над токен-счётом через `SetAuthority`. Плюс hook требовал второй программы из-за запрета повторного входа.

**Новая схема:**

- mint облигации создаётся с `DefaultAccountState = Frozen`, freeze authority — PDA `Bond`;
- все токен-счета облигации **всегда заморожены**. У замороженного счёта Token-2022 отклоняет перевод, сжигание, `Approve` и смену authority (подтверждено по [исходнику Token-2022](https://raw.githubusercontent.com/solana-program/token-2022/main/program/src/processor.rs), ревью 2026-09-27). **Исключения:** `CloseAccount` при нулевом балансе и `WithdrawExcessLamports` (только лишние lamports) — реестр не ломают, но пустой ATA может исчезнуть, поэтому инструкции пересоздают его идемпотентно (§5.6). Проверяем тестом;
- любое движение облигации — только инструкция `pritok`: разморозить → mint / transfer / burn → заморозить, в одной транзакции, вместе с обновлением реестра;
- принимаются только **канонические ATA** держателя (Token-2022 ATA имеют `ImmutableOwner`). Один кошелёк — один счёт, неоднозначностей сверки нет.

**Что это даёт:**
- обход реестра невозможен: изменить баланс можно только через программу, а программа всегда пишет реестр;
- **одна программа** вместо двух: цепочка `pritok → Token-2022` без обратного вызова, повторного входа нет;
- не нужны `ExtraAccountMetaList`, проверка флага `transferring`, hook-хелперы для CPI;
- сделка с двумя подписями (`trade_dvp`) — обычная инструкция этой же программы.

**Цена:** облигацию нельзя отправить из Phantom напрямую — только через интерфейс PRITOK. Для ценной бумаги с KYC это правильное поведение: перевод без регистратора в реальности тоже невозможен. В README это подаётся как свойство, а не ограничение.

**Отвергнутые варианты:**
- transfer hook — см. выше;
- расширение [Permissioned Burn](https://solana.com/docs/tokens/extensions/permissioned-burn) — закрывает только сжигание, требует Token-2022 v11 и отдельной загрузки программы в локальный валидатор;
- заморозка на отсечке + офчейн-снимок + Merkle root (как в [Owed](https://github.com/thesithunyein/owed)) — слабее по проверяемости onchain.

### 5.1 Токены

- **Облигация** — Token-2022 mint:
  - `DefaultAccountState = Frozen`, freeze authority и mint authority — PDA `Bond`;
  - `MetadataPointer` + `TokenMetadata` — название выпуска, тестовый ISIN-подобный код;
  - `PermanentDelegate` **не используем**: эмитент не должен уметь забрать бумаги.
- **Деньги** — свой mint **tKZT** на devnet (2 знака, как тиыны), кран в интерфейсе.
  `Bond.payment_mint` — параметр, но **не «любой SPL-токен»**: `create_bond` принимает только mint из списка `Config.payment_mints`, который ведёт оператор, и отклоняет Token-2022 mint с `TransferFee`, `TransferHook` и другими расширениями, меняющими сумму или путь перевода. Иначе vault получит меньше, чем записано в `funded`, и последним держателям не хватит ([transfer fees](https://solana.com/docs/tokens/extensions/transfer-fees)). KZTE добавляется в список после проверки его расширений.

### 5.2 Аккаунты (PDA)

| Аккаунт | Поля |
|---|---|
| `Config` | `operator`, `paused`, `payment_mints` (разрешённые денежные токены) |
| `Bond` | `issuer`, `bond_mint`, `payment_mint`, `face_value`, `coupon_bps`, `period_secs`, `start_ts`, `record_offset_secs`, `num_periods`, `factor_bps` (текущий, 10 000 = 100%), `subscription_end_ts` (< первой отсечки), `issued_units` (фиксируется при закрытии подписки, дальше не меняется), `supply` (ещё не сожжённые облигации), `reserved` (внесённые и ещё не выплаченные onchain-обязательства), `status` (Placement / Active / Matured / Closed), `schedule: [(record_ts, action_id); MAX_EVENTS]` — **отсортирован по времени отсечки**, `schedule_len` |
| `Holder` (по `bond` + кошелёк) | `allowed`, `balance`, `synced_upto` (сколько первых событий графика уже зафиксировано), `bal_at: [u64; MAX_EVENTS]` |
| `Event` (**внутри `Bond.events`**, не отдельный аккаунт — решение при реализации 2026-09-27) | `action_id`, `kind` (Coupon / PartialRedemption / Maturity), `record_ts`, `pay_ts`, `factor_bps_applied` (фактор, от которого считается событие), `amount_per_unit`, `funded`, `claimed`, `mode` (Onchain / Bank), `status` (Scheduled / Funded / Defaulted). `required = amount_per_unit × issued_units` вычисляется, не хранится |
| `PaymentVault` | ATA `payment_mint`, владелец — PDA `Bond`; снять может только программа |
| `Claim` (по `action` + держатель) | `amount`, `status` (Paid / BankRequested / BankConfirmed), `bank_ref_hash` — квитанция и защита от двойной выплаты |

`MAX_EVENTS = 8`: 4 купона + погашение + до 3 внеплановых действий. Жёсткий предел, проверяется при создании.

### 5.3 Дата отсечки (главная техническая часть)

`action_id` — просто имя события. Для отсечек используется **позиция в хронологическом графике** `Bond.schedule`.

**При любом изменении баланса держателя** (подписка, перевод, погашение) в момент `now`, до изменения:

```
while synced_upto < schedule_len and schedule[synced_upto].record_ts <= now:
    bal_at[synced_upto] = balance
    synced_upto += 1
balance = новый баланс
```

**Право на событие в позиции i** (только если `record_ts(i) <= now`):
- `i < synced_upto` → `bal_at[i]`;
- иначе → `balance` (после отсечки баланс не менялся).

**Почему это корректно:**
- `bal_at` не вытесняется: места хватает на все события выпуска, запись живёт, пока жив выпуск;
- пропуск нескольких отсечек без движения баланса заполняется одним циклом одинаковым значением;
- **внеплановое действие** вставляется в `schedule` по месту, только если его `record_ts > now`. Все события правее тоже в будущем, значит ни один держатель их ещё не зафиксировал — сдвиг позиций безопасен;
- число облигаций на любую отсечку = `Bond.issued_units`. Подписка закрывается (`subscription_end_ts`) строго до первой отсечки, `issued_units` записывается один раз и больше не меняется. Сжигание при погашении уменьшает только `supply` и на расчёт `required` не влияет;
- **равные `record_ts`** (амортизация в дату купона) допустимы: цикл использует `<=`, оба события получают один и тот же баланс.

**Отсечка погашения закрывает переводы.** После `record_ts` события Maturity инструкции перевода и сделки отклоняются: право на номинал и токен для сжигания должны оставаться у одного держателя. После отсечек купонов и частичного погашения переводы разрешены.

**Обязательные тесты** (пишутся до основной логики):
1. перевод до и после отсечки — купон у правильного держателя;
2. держатель пропускает 3 события, потом много переводов, потом забирает первое — сумма верная;
3. внеплановое действие между купонами 2 и 3 — купон 3 считается по новому номиналу, позиции не сбиваются;
4. попытки `BurnChecked`, `Transfer`, `SetAuthority`, `Approve` напрямую через Token-2022 — все падают;
5. перевод после отсечки погашения — отклонён;
6. двойной `claim` — отклонён;
7. часть держателей погашает облигации, остальные потом забирают купон 4 — `required` и выплаты верны;
8. амортизация объявлена до купона 2: купон 2 — от 100%, купон 3 — от 80%; прошедшие события свою сумму не меняют;
9. равные `record_ts` и все порядки «вставка → перевод → отсечка → claim»;
10. держатель закрыл пустой ATA, затем получает перевод или подписку — счёт пересоздаётся замороженным, `Holder` и права целы;
11. `claim` по банковскому событию через onchain-путь — отклонён; инвариант `vault ≥ reserved` после каждой операции.

### 5.4 Расчёт прав и долг эмитента

- Купон на единицу = `face_value × factor_bps_applied / 10 000 × coupon_bps / 10 000 / 2`, где `factor_bps_applied` — фактор **на начало купонного периода** (купон начисляется на номинал, который был в обращении весь период).
- Частичное погашение на единицу = `face_value × Δfactor`.
- Погашение на единицу = `face_value × factor`; купон 4 — отдельное событие, но выплачиваются они одной инструкцией `redeem` (§5.6).
- `required = amount_per_unit × issued_units`.

**Когда меняется номинал (амортизация).** Частичное погашение происходит **только в дату одного из будущих купонов** (стандарт для амортизируемых облигаций): его `record_ts` и `pay_ts` совпадают с купоном k, объявить его можно, только пока отсечка купона k не наступила. Купон k считается от старого фактора, купоны после k и погашение — от нового. При объявлении программа пересчитывает `factor_bps_applied` и `amount_per_unit` только у событий после k — все они ещё в будущем. Прошедшие события свою сумму не меняют. `Bond.factor_bps` переключается в `pay_ts` события амортизации.

**Выплата «всё или ничего» по событию:**
- `claim` открыт только при `funded >= required`;
- после `pay_ts` при `funded < required` кто угодно вызывает `mark_default` → статус `Defaulted`, долг `required − funded` виден в реестре;
- эмитент может довнести в любой момент → статус `Funded`, выплаты открываются. **Долг не прощается и не пропорционируется.**

**Частичное погашение финансируется при объявлении:** `declare_partial_redemption` в одной транзакции вносит полную сумму. Ситуации «номинал уменьшили, а денег не заплатили» нет.

**Резерв счёта выплат.** Все onchain-события делят один `PaymentVault`, поэтому:
- `fund_action` (onchain) переводит токены и увеличивает `Action.funded` и `Bond.reserved`; `claim` уменьшает `Bond.reserved`;
- `claim` проходит, только если статус события `Funded` и `Action.claimed + amount ≤ Action.funded`;
- после каждой операции проверяется инвариант `баланс vault ≥ Bond.reserved`;
- банковские события **никогда** не трогают vault и `reserved`; onchain-`claim` по ним отклоняется.

**Закрытие выпуска:** статус `Closed` — когда `supply = 0` и ни у одного события нет долга. `Closed` **не блокирует** `claim` и банковские подтверждения по уже возникшим правам: невостребованные деньги остаются доступны держателю. В реестре по каждому событию три числа: нужно (`required`), внесено (`funded`), выплачено (`claimed`).

**Округление:** каждому держателю вниз до тиына. Пыль остаётся на счёте выплат навсегда. Эмитент **ничего не выводит** со счёта выплат в MVP — нет `withdraw_remainder`, нет риска забрать невостребованные деньги держателей.

### 5.5 Два пути выплаты

**Onchain (по умолчанию):** эмитент вносит tKZT на `PaymentVault` → держатель вызывает `claim` → `Claim` создаётся, tKZT переводятся.

**Банковский путь** (`settlement_mode = Bank`, задаётся для события):

1. После отсечки держатель (или оператор за него) создаёт `Claim` в статусе `BankRequested` — поручение «держателю X причитается N ₸».
2. Эмитент отмечает, что перевёл общую сумму платёжному агенту (`fund_action` без токенов — отметка + хеш платёжки).
3. Оператор после банковского перевода вызывает `confirm_bank_payment(claim, bank_ref_hash)` → `BankConfirmed`.

**Честная граница:** это заявление оператора, а не доказательство платежа. Интерфейс пишет «подтверждено оператором, банковская выплата симулирована». В реальной интеграции нужно сверяемое подтверждение от банка или платёжного агента (подпись банка, выписка). Банковские реквизиты onchain не хранятся — только хеши.

**Отзыв допуска и пауза не отменяют права.** `revoke_holder` запрещает получать облигации, `pause` приостанавливает движения облигаций, но `claim` уже возникших выплат работает всегда.

### 5.6 Инструкции (одна программа `pritok`)

| Кто | Инструкция |
|---|---|
| Оператор | `init_config`, `set_payment_mints`, `allow_holder` (создаёт `Holder` и замороженный ATA), `revoke_holder`, `set_paused`, `confirm_bank_payment` |
| Эмитент | `create_bond` (mint + плановые `Action` + график), `close_subscription` (фиксирует `issued_units`; также автоматически при первой операции после `subscription_end_ts`), `fund_action`, `declare_partial_redemption` (только в дату будущего купона, с полной оплатой) |
| Инвестор | `subscribe` (tKZT → mint облигаций, до `subscription_end_ts`), `transfer_bond`, `claim`, `redeem` (burn → номинал + невыплаченный купон 4, две квитанции `Claim` в одной инструкции), `request_bank_claim` |
| Кто угодно | `mark_default` |
| Бонус | `trade_dvp` (чистая цена от сторон, НКД считает программа, две подписи) |

Каждая инструкция, двигающая облигацию: разморозить → операция → заморозить, реестр обновляется в той же инструкции. `subscribe`, `transfer_bond` и `trade_dvp` создают канонический ATA получателя идемпотентно (`create_idempotent`, плательщик — подписант): если держатель закрыл пустой счёт, он пересоздаётся замороженным, `Holder` и прошлые права не затрагиваются.

### 5.7 Интерфейс

Одно Next.js-приложение, переключатель ролей в шапке. Для видео — заранее созданные devnet-кошельки в браузере (только devnet); Phantom — опционально.

| Экран | Содержимое |
|---|---|
| **Публичный реестр** (главный) | держатели и доли; таймлайн событий; по каждому событию — «держатель → баланс на отсечку → сумма → статус → транзакция/платёжка», долг эмитента, ссылки на эксплорер |
| **Эмитент** | мастер выпуска; график «нужно внести / внесено / долг»; пополнить; объявить частичное погашение |
| **Инвестор** | мои облигации; ближайшие выплаты; забрать; перевести; погасить; (бонус) продать |
| **Оператор** | KYC-список; очередь банковских поручений; пауза |
